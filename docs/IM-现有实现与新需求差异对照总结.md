# IM 现有实现与新需求差异对照总结

> 对照日期：2026-08-10  
> 新需求来源：[IM 产品原型需求文档](./IM-产品原型需求文档.md)  
> 详细改造分析：[IM 产品需求服务端改造分析报告](./IM-产品需求服务端改造分析报告.md)  
> 对照对象：`chat-0.25.3` 当前服务端源码

## 1. 文档目的

本文从“现有服务端已经实现了什么”出发，对照新产品需求逐项给出处理结论：

- **保留**：现有实现已基本满足需求，只补配置或测试；
- **需修改**：现有能力可复用，但协议、数据模型、权限或流程不完整；
- **新增**：现有系统没有对应实现，需要新增模块；
- **客户端为主**：主要是移动端交互，服务端只提供状态、配置或资源；
- **废弃**：现有产品能力或接入方式在新需求中没有对应章节，不再作为新产品能力继续建设。

“新需求无直接章节”的数据库、对象存储、集群、监控等运行基础设施不按产品功能废弃，而标记为“保留基础设施”。真正需要废弃的能力单列在第 5 节。

## 2. 总体结论

当前系统可以继续作为新产品的即时通讯内核，不需要重写。现有 P2P Topic、群 Topic、Subscription ACL、消息序号、消息广播、回执、文件上传、Push 和 WebRTC 信令均可复用。

新需求与现状的主要关系如下：

| 新需求章节 | 功能域 | 当前覆盖程度 | 结论 |
| --- | --- | --- | --- |
| 第 1 章 | 账号、企业码、短信、实名、独立密码 | 部分覆盖 | 认证内核保留，产品流程需修改，企业码/实名需新增 |
| 第 2 章 | 会话首页、网络状态、消息操作、系统消息 | 部分覆盖 | 会话与连接保留，产品状态和系统通知需修改 |
| 第 3 章 | 单聊、好友状态、回执、媒体和名片 | 部分覆盖 | P2P/回执保留，好友约束和结构化消息需修改 |
| 第 4 章 | 输入、@、语音、文件、收藏、转发 | 少量覆盖 | 文件和通用消息可复用，大部分产品语义需新增 |
| 第 5 章 | 通讯录、好友申请、主页、黑名单 | 少量覆盖 | 用户搜索可改造，关系状态机需新增 |
| 第 6 章 | 群创建、审批、公告、管理、禁言、群文件 | 部分覆盖 | 群和 ACL 保留，群治理业务需新增 |
| 第 7 章 | 收藏、下载、聊天记录搜索 | 少量覆盖 | `slf` 和文件可复用，授权和索引必须修改 |
| 第 8 章 | 语音/视频通话 | 部分覆盖 | P2P WebRTC 信令保留，通话业务状态需修改 |
| 第 9 章 | 组织、会议、日报、月报、信箱 | 未覆盖 | 全部新增业务模块 |
| 第 10 章 | 资料、设置、版本、隐私、青少年模式 | 少量覆盖 | 通用资料可改造，其余多数新增或客户端实现 |
| 第 11 章 | 反诈、举报、反馈 | 未形成业务闭环 | 插件机制保留，业务模型和处置流程新增 |

必须优先处理三个基础问题：

1. 消息发布缺少客户端消息 ID 幂等校验，断线重试可能产生重复消息；
2. 文件下载只校验登录，没有校验用户对文件关联 Topic/消息的读取权限；
3. 当前核心表没有 `tenant_id`，共享数据库部署多个企业前必须完成全链路租户隔离。

## 4. 按新需求章节逐项对照

### 4.1 第 1 章：账号注册、登录与身份安全

| 新需求章节 | 新功能 | 当前实现 | 是否改 | 如何修改 |
| --- | --- | --- | --- | --- |
| 1.1 | 企业码登录 | 无企业/租户模型 | 新增 | 增加企业码解析 API、企业状态、服务地址和认证策略；共享库模式需先加 `tenant_id` |
| 1.2-1.3 | 账号密码登录及错误提示 | basic + token 已有 | 需修改 | 增加协议确认、统一错误码、失败计数、账号锁定、设备登录记录和安全通知 |
| 1.4-1.5 | 短信注册和倒计时 | 电话验证器已有 | 需修改 | 新增注册流程 API；验证码按用途隔离，返回有效期和重发时间，服务端强制限频 |
| 1.6 | 忘记密码 | 验证器与密码更新能力分散 | 需修改 | 建立“发码 → 临时票据 → 重置”状态机；成功后撤销旧 Token |
| 1.7 | 敏感操作二次验证 | 无统一业务流程 | 新增 | 增加验证挑战、一次性票据、有效期、错误次数和操作绑定 |
| 1.8-1.10 | 实名认证及状态提醒 | 无 | 新增 | 独立实名表、字段加密、审核状态、脱敏查询、审核回调和提醒消息 |
| 1.11 | 四位独立密码 | 无 | 新增 | 保存强哈希、失败锁定和找回流程；禁止写入普通设置 JSON 或明文日志 |

## 5. 新需求未覆盖的现有能力：废弃清单

以下能力在新需求文档中没有对应章节。按新产品范围标注为“废弃”，但应采用“停止新接入 → 观察存量 → 迁移 → 删除”的方式处理，不能在未确认线上使用情况时直接删除源码或数据。

| 现有能力 | 源码/配置 | 新需求章节 | 处理结论 | 废弃方式 |
| --- | --- | --- | --- | --- |
| 匿名登录 | `server/auth/anon` | 无 | **废弃** | 新环境不配置、不向客户端公开；确认无匿名会话后移除注册和文档 |
| 邮箱注册/邮箱验证码/邮箱找回 | `server/validate/email` | 无，新需求只定义手机号短信 | **废弃** | 产品 API 不再暴露 email credential；存量账号先绑定手机号再停用 |
| Channel 只读广播 Topic | `TopicCatGrp` 的 channel 模式 | 无 | **废弃** | 禁止新建 Channel；如有存量，迁移为普通群或公告业务后再移除入口 |
| Long Poll 客户端接入 | `/v0/channels/lp` | 无，新移动端按 WebSocket 设计 | **废弃** | 先记录调用量并公告；无流量后关闭路由，WebSocket 保留 |
| 客户端 gRPC 接入 | `grpc_listen`、客户端 gRPC 服务 | 无 | **废弃** | App 不再接入；注意保留插件所需的 gRPC 能力，两者不能一起误删 |
| 示例 Python Chat Bot | `tinode.conf` 中 `python_chat_bot` | 无 | **废弃** | 从生产配置删除；插件框架因第 11 章风控继续保留 |
| 静态网页托管 | `main.go` 静态文件路由/配置 | 无 Web 产品章节 | **废弃** | 新产品服务端不托管 Web UI；确认运维页面用途后关闭 |

## 10. 废弃实施规则

废弃项不要直接删除，应按以下顺序执行：

1. 在配置和对接文档中标记 deprecated，禁止新客户端接入；
2. 为废弃入口增加调用指标，至少观察一个完整客户端版本周期；
3. 对匿名账号、邮箱账号、Channel 等有数据的能力先做存量扫描；
4. 给存量用户提供迁移方案，例如邮箱账号绑定手机号、Channel 迁移普通群；
5. 新版本服务端默认关闭，保留临时回退开关；
6. 确认无调用和无未迁移数据后，再删除路由、配置、代码和测试；
7. 数据库删除列或表必须单独发布，保留备份和回滚窗口。

客户端 gRPC 和 Plugin gRPC 必须分开处理：新需求没有客户端 gRPC，因此前者废弃；第 11 章需要外部审核插件，因此 Plugin Firehose 及其 gRPC 通道保留。

## 11. 验收口径

每项改造只有同时满足以下条件才算完成：

1. 文档中的新需求章节有对应 API/协议、数据表和权限规则；
2. 旧客户端兼容行为有明确结论，不依赖未定义 JSON 字段；
3. 重试、并发、断网恢复不会产生重复业务数据；
4. 用户不能通过直接构造协议绕过好友、黑名单、禁言、隐私和青少年策略；
5. 文件、搜索、转发和收藏均重新执行当前用户的资源权限；
6. 共享 SaaS 模式下通过跨租户负向测试；
7. 审批、实名、举报、群管理和匿名信箱敏感操作有审计记录；
8. 废弃入口有调用量证据和存量迁移结果，不能仅凭新原型没有页面就直接删除；
9. MySQL schema、升级脚本、回滚脚本和代码中的建表定义保持一致；
10. 服务端单元测试、MySQL 集成测试、WebSocket/HTTP 端到端测试和真实设备通话测试全部通过。

## 12. 最终处理建议

新系统应保留 Tinode 的实时消息内核，重点修改认证流程、消息协议、权限策略、文件授权和通话状态；好友、群治理、搜索、企业工作台、实名、青少年和举报作为新的产品业务层建设。

新需求未覆盖的匿名登录、邮箱注册验证、Channel、Long Poll、客户端 gRPC、示例聊天机器人和静态网页托管标记为废弃。多数据库 Adapter 是否物理删除取决于产品数据库决策；若产品版确定只支持 MySQL，则 PostgreSQL、MongoDB 和 RethinkDB 不再承担新业务适配与验收。

改造顺序应先处理租户、消息幂等和文件授权，再完成好友与基础消息，随后完成群治理、搜索、通话与安全，最后建设企业工作台。这样可以最大限度复用现有实现，同时避免继续维护新产品不需要的入口和功能。
